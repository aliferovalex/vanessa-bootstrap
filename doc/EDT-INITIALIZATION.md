# Инициализация проекта EDT

Этот форк добавляет импорт существующей базы в структуру vanessa-bootstrap.
По умолчанию проект инициализируется в клонированном каталоге шаблона с сохранением его истории Git. Требуются Windows PowerShell
5.1 или 7, Git, Git LFS, толстый клиент 1С и современный 1cedtcli.exe.

```powershell
git clone https://github.com/aliferovalex/vanessa-bootstrap.git
cd vanessa-bootstrap
.\initialize.cmd -InfobaseType File -Infobase D:\Bases\Demo -DesignerPath C:\Tools\1C\bin\1cv8.exe -EdtCliPath C:\Tools\EDT\1cedtcli.exe -ProjectName Demo -AskCredential
```

Сначала можно добавить `-Preview`. Для отдельного режима `-TargetDirectory` каталог назначения должен отсутствовать.
Пути программ в примере замените на свои. Для серверной базы используйте
`-InfobaseType Server -Infobase server\base`.
Без `-InfobaseType` появляется меню: `1` — File, `2` — Server,
`3` — Repository. Некорректный номер можно ввести повторно.

Для аутентификации ОС укажите `-UseOSAuthentication` вместо `-AskCredential`:

```powershell
.\initialize.cmd -FreshHistory -GitBranch main -UseOSAuthentication
```

При выгрузке основной конфигурации и расширений Конфигуратору передаётся
`/WA+`, без `/N` и `/P`. Используется текущая учётная запись Windows;
в базе у пользователя должны быть настроены аутентификация ОС и доступ
к Конфигуратору. Режим поддерживает `File`/`Server`, но не прямой доступ к
хранилищу `Repository`. Нельзя совмещать с `-AskCredential`, `-UserName`,
`-Password`. В явном режиме имени/пароля 1С передаётся `/WA-`.

В основном режиме сохраняются `.git`, текущая ветка и remotes. Исходники
готовятся в отдельном временном клоне, затем коммит применяется fast-forward.
Рабочая копия должна быть чистой, манифест и исходники должны отсутствовать.
Заглушки README в `src/cf` и `src/cfe` заменяются EDT-проектами. Перед публикацией
повторно проверяются HEAD и ветка. `-SkipInitialCommit` оставляет изменения
в индексе. `-ProjectRemoteUrl` меняет `origin`, сохраняя прежний как `bootstrap`.
В интерактивном запуске адрес предлагается в конце; пустой ответ сохраняет origin.

Явный `-TargetDirectory` с новым адресом включает прежний отдельный режим:
копируются отслеживаемые файлы шаблона, создаётся новая история `main` без remote.
Перед инициализацией завершите локальные изменения шаблона коммитом.

Основная конфигурация находится в `src/cf`, расширения — в `src/cfe/<имя>`.
По умолчанию берутся все расширения. `-NoExtensions` исключает их,
`-Extensions` позволяет выбрать список при прямом запуске PowerShell-скрипта.
Для выбора из списка подключённых к базе расширений добавьте `-SelectExtensions`.
После выгрузки скрипт покажет имена с номерами: введите `1,3`, `*` для всех
или `0` для проекта без расширений. Некорректный ввод можно повторить.
При полностью интерактивном запуске `initialize.cmd` без параметров этот выбор
появляется автоматически. В автоматических сценариях без `-SelectExtensions`
поведение сохраняется: все расширения либо явно заданный `-Extensions`.
Выбор выполняется перед преобразованием в EDT; для обнаружения списка XML
всех расширений сначала выгружается во временный каталог.
`-NoGitLfs` отключает LFS. Существующие правила окончаний строк сохраняются.

Для базы, уже привязанной к хранилищам, можно передать `-RepositoryUserName`.
Пароль запрашивается скрыто. Привязка и исходная конфигурация не изменяются.
Поддержан также прямой импорт из хранилищ:

```powershell
.\initialize.cmd -InfobaseType Repository -Infobase https://server/repo/repo.1ccr/Main -RepositoryVersion 12 -RepositoryUserName reader -TargetDirectory D:\Projects\Demo -DesignerPath C:\Tools\1C\bin\1cv8.exe -EdtCliPath C:\Tools\EDT\1cedtcli.exe
```

Пароль хранилища запрашивается скрыто. Можно использовать `-AskCredential`:
имя запрашивается в консоли, пароль вводится скрыто. Для источника `Repository`
это пользователь хранилища; для `File`/`Server` — пользователь информационной
базы 1С. При ошибке «Пользователь ИБ не идентифицирован» сначала проверьте
эти имя и пароль в обычном Конфигураторе той же базы. Для входа Windows
в базу используйте отдельный параметр `-UseOSAuthentication`.
При прямом вызове PS1 пароль можно передать как SecureString; в файлы проекта он
не записывается. Платформа получает пароль аргументом процесса, доступным
административным средствам ОС. URL со встроенными учётными данными запрещены.

`-RepositoryVersion -1` (по умолчанию) получает актуальное состояние. Для
воспроизводимости укажите положительный номер версии. Для расширений передайте
`-ExtensionRepositoryFile D:\Settings\repositories.json` с массивом:

```json
[{"name":"Extra","url":"https://server/repo/repo.1ccr/Extra","version":4}]
```

Все хранилища читаются одной учётной записью, одной версией платформы. Список
расширений задаётся явно: основное хранилище не предоставляет их перечень.
Создаётся отдельная временная база, сначала читается конфигурация, затем CFE
расширений в её контексте. Захват, привязка и помещение не выполняются.
Для обращения через общий прокси заранее настройте разрешённые привязки проекта;
неизвестный alias прокси отклоняет. Прямой адрес публикации 1С тоже поддерживается.

Манифест сохраняет адреса и запрошенные версии без паролей. Он не утверждает,
что версии разных хранилищ являются согласованным снимком. Основы синхронизации
по-прежнему подтверждаются отдельно в сервисе.

Для регистрации рабочей области добавьте `-RegisterEdtStart`.
Если EDT Start запущен, закройте его либо добавьте `-RestartEdtStart`.
Личную базу отладки настройте отдельно. Автоматический обмен с хранилищем
не включается: основы синхронизации подтверждаются в сервисе.

Для EDT-проектов Windows-команды `build.cmd`, `prepare.cmd`, `update.cmd`
вызывают `tools/Run-Project.ps1`. Задайте `ONEC_EDT_CLI`, `ONEC_DESIGNER` и при
необходимости `ONEC_EDT_INI` в окружении или передайте одноимённые параметры
`-EdtCliPath`, `-DesignerPath`, `-EdtIniFile`.

`build.cmd` копирует EDT-исходники в отдельный рабочий каталог, преобразует
конфигурацию и расширения в XML, собирает CF/CFE в новой файловой базе. Версия
Конфигуратора должна точно совпадать с `platformVersion`. OneScript для этой
сборки не требуется. Артефакты и журналы находятся в `build/edt-<UUID>`;
`result.json` появляется только после успешного выполнения. Исходники не
перезаписываются, предыдущие сборки не удаляются.

`prepare.cmd` и `update.cmd` после сборки передают XML в vanessa-runner,
загружают расширения и выполняют обновление в режиме Предприятия. Эти команды
изменяют базу из `env.json` (по умолчанию `build/ib`); настройте её перед запуском.
Они используют API **vanessa-runner 2.6.x**, например 2.6.1, и требуют OneScript.
vanessa-runner 3.x использует другие команды и здесь пока не поддерживается.
Для дополнительных параметров runner используйте PowerShell:
`tools/Run-Project.ps1 -Action Prepare -RunnerArguments @('--db-user','Developer')`.

Отдельный экспорт без сборки: `tools/Export-Edt.ps1 -EdtCliPath ...`.
Старые XML-проекты продолжают использовать прежние команды bootstrap.
Shell-скрипты пока сохраняют прежнее ограничение для EDT; новая сборка рассчитана
на Windows. Команда `test` также использует vanessa-runner 2.6.x.

Пароли и параметры личных баз в шаблон не добавляются. Промежуточные выгрузки
и журналы остаются рядом с новым проектом в `.project-init-<UUID>`;
после проверки их можно удалить. Они не входят в репозиторий проекта.

Обновления upstream получают в рабочую копию шаблона отдельно:
`git fetch upstream`, затем проверка и слияние выбранного коммита.
Существующие проекты автоматически не обновляются и не перезаписываются.

## Выбор ветки при инициализации

Передайте `-GitBranch`, например:

```powershell
.\initialize.cmd -GitBranch main -AskCredential
```

При интерактивном запуске имя ветки также запрашивается с текущим значением
по умолчанию. Без параметра в клоне сохраняется текущая ветка; для отдельного
нового каталога используется `main`. `-GitBranch develop` или `feature/start`
задаёт другое имя.

В клоне новая ветка создаётся из подготовленного коммита инициализации только
после успешной выгрузки и проверок. Исходная ветка остаётся на прежнем коммите.
Чтобы использовать уже существующую другую ветку, сначала переключитесь на неё
через `git switch`, затем запускайте инициализацию. Скрипт не перезаписывает
существующие ветки. С `-SkipInitialCommit` новая ветка остаётся на исходном
коммите, а подготовленные изменения находятся в индексе.

Отдельный репозиторий: `initialize.cmd -TargetDirectory D:\Projects\Other -GitBranch develop`.
Параметр не создаёт ветку на сервере Git и не выполняет push.

## Новый проект без истории шаблона

```powershell
.\initialize.cmd -FreshHistory -GitBranch main -AskCredential
```

`-FreshHistory` создаёт независимый Git в этом же каталоге: один начальный коммит
с готовым проектом, без старых коммитов, веток и remotes шаблона. Без флага
история сохраняется. По умолчанию новая ветка называется `main`; другое имя
задаётся через `-GitBranch`. `-SkipInitialCommit` оставляет новый Git без коммитов
с подготовленными файлами в индексе.

Сначала все исходники и Git готовятся во временном каталоге. Старый `.git`
сохраняется вне проекта в `.project-init-<UUID>/previous-project/.git`; путь
выводится после применения. Резервная копия содержит прежнюю историю и настройки,
не входит в новый репозиторий и не отправляется при push. После проверки её
можно удалить самостоятельно. Ошибка применения вызывает восстановление
прежних файлов и `.git`; сведения о публикации — в `fresh-history-publication.json`.

Режим доступен для самостоятельного клона без дополнительных Git worktrees.
Рабочая копия должна быть чистой, исходники и манифест должны отсутствовать.
Для подключения Git-сервера задайте `-ProjectRemoteUrl` либо выполните
`tools/git-project-init.cmd` после инициализации. При `-FreshHistory` старые
remotes остаются только в резервной копии. С явным другим `-TargetDirectory`
история и так создаётся заново, поэтому дополнительный флаг там не требуется.
